2. Full Send-Message Flow

From pressing Enter to the assistant response streaming into the UI. This is the single most important flow in the app.

A->>A: createMessage("user"), createMessage("assistant") A->>DB: applyLocalInsert (optimistic) A->>PO: dispatch("create_user_message", payload, {opId}) PO->>WS: JSON.stringify({type:"command", opId, ...}) WS->>DO: WebSocket message DO->>DO: processChatCommand(opId, "create_user_message", payload) DO->>DO: dedup check (getCommandAck) DO->>DO: decodeCommand (Effect Schema validation) DO->>CH: handleCreateUserMessage(opId, payload, ctx) CH->>CH: normalizeThread, normalizeMessage ×2 CH->>ES: insertEvent("thread_upserted") CH->>ES: insertEvent("message_upserted" ×2) ES->>SQL: INSERT INTO events + INSERT OR REPLACE INTO threads/messages SQL-->>ES: events with serverSeq ES-->>CH: SyncServerEvent[] CH-->>DO: {events, followUp: DeferredFollowUp} DO->>SQL: INSERT INTO commands (ack) DO->>WS: broadcast(ack) + broadcast(events) WS->>SA: onmessage (envelopes) SA->>SA: processEnvelopes() SA->>DB: apply mutations (batched) DO->>DO: saveTurnParams + setAlarm DO->>AT: ctx.waitUntil(runAssistantTurn(...)) 5. Event Sourcing: Read Path (Snapshot)

When a client connects or a protocol mismatch occurs, the server builds and sends a full snapshot of all materialized tables.

7. Assistant Turn (Streaming)

How runAssistantTurn() orchestrates tool calls, streams the AI response, and broadcasts deltas back to the client.

AT->>TanStack: chat({adapter, messages, systemPrompts, tools, agentLoop, signal}) TanStack->>Upstream: HTTP POST with SSE Upstream-->>TanStack: SSE stream (AG-UI format) TanStack-->>AT: AsyncIterable<ExtendedStreamChunk> AT->>SC: consumeAssistantStream(stream, deps) loop per chunk SC->>SC: process chunk type alt TEXT_MESSAGE_CONTENT SC->>SC: accumulate delta, flush at 96-char threshold SC->>ES: appendServerEvent("message_delta", {messageId, delta}) ES-->>SC: SyncServerEvent SC->>WS: broadcast(event) else CUSTOM (reasoning) SC->>SC: accumulate reasoning delta SC->>ES: appendServerEvent("message_part_appended", {row}) ES-->>SC: SyncServerEvent SC->>WS: broadcast(event) else TOOL_CALL_START SC->>Search: execute search tool Search->>Exa: HTTP search API Exa-->>Search: results Search->>ES: search_runs_replaced + search_results_replaced ES-->>SC: events SC->>WS: broadcast(events) else TOOL_CALL_START (extract) SC->>Extract: execute extract tool Extract->>Browser: Cloudflare Browser Rendering Browser-->>Extract: page content Extract->>ES: extract_runs_replaced ES-->>SC: events SC->>WS: broadcast(events) else RUN_FINISHED SC->>SC: flush final delta SC->>ES: appendServerEvent("message_completed", {text, tokens, durationMs, ...}) ES-->>SC: SyncServerEvent SC->>WS: broadcast(event) SC-->>AT: StreamConsumerResult else RUN_ERROR SC->>ES: appendServerEvent("message_failed", {errorCode, errorMessage}) ES-->>SC: SyncServerEvent SC->>WS: broadcast(event) end end AT->>Rec: finishSpan (root) + finishTraceRun AT-->>DO: return

8. Retry vs Edit vs Fork

Three ways to create a new assistant response, each with a different data model.
sequenceDiagram participant U as User participant A as actions.ts participant DB as TanStack DB participant WS as WebSocket participant S as Server Note over U,S: === RETRY === U->>A: retryMessageAction(thread, userMessage, ...) A->>A: createMessage("assistant", status:"pending") A->>DB: applyLocalInsert(newAssistant) A->>WS: dispatch("retry_message", {userMessage.id, assistantMessage, ...}) WS->>S: command S->>S: handler: upsert thread + insert assistant message S->>S: runAssistantTurn (reuse existing user message) S-->>WS: events (thread_upserted, message_upserted) WS-->>DB: sync Note over DB: Old assistant message stays,
new one appears as child of same user message Note over U,S: === EDIT === U->>A: editUserMessageAction(thread, sourceMessage, newText, ...) A->>A: createMessage("user", sourceMessageId:source.id, status:"completed") A->>A: createMessage("assistant", status:"pending") A->>A: clone attachments A->>DB: applyLocalInsert(newUser + newAssistant + clonedAttachments) A->>WS: dispatch("edit_user_message", {sourceMessageId, userMessage, assistantMessage, attachments}) WS->>S: command S->>S: handler: upsert thread + insert user+assistant+attachments S->>S: runAssistantTurn S-->>WS: events WS-->>DB: sync Note over DB: New branch created:
original messages preserved,
sourceMessageId links back Note over U,S: === FORK === U->>A: forkThreadAction(sourceThreadId, sourceMessageId, workspaceId) A->>A: walk message path to fork point A->>A: create new thread (forkedFromThreadId, forkedFromMessageId) A->>A: clone messages (sourceMessageId links) + clone attachments A->>DB: applyLocalInsert(newThread + clonedMessages + clonedAttachments) A->>WS: dispatch("fork_thread", {...}) WS->>S: command S->>S: handler: validate source, insert thread+messages+attachments S-->>WS: events WS-->>DB: sync Note over DB: Entirely new thread with
copied history up to fork point

9. Crash Recovery via Alarm

If the DO restarts mid-turn (eviction, migration), the alarm mechanism recovers interrupted assistant responses.
sequenceDiagram participant DO as SyncEngineDO (new instance) participant SQL as SQLite participant AT as assistant-turn.ts participant WS as WebSocket Note over DO: DO created after eviction/restart DO->>SQL: initializeStorage() (DDL + protocol check) DO->>DO: alarm() fires DO->>SQL: loadAllTurnParams() SQL-->>DO: Map<messageId, SavedTurnParams> loop for each pending turn DO->>DO: check activeTurnMessageIds alt still active in this instance DO->>DO: reschedule alarm else stale (DO was restarted) DO->>SQL: getMessage(staleMessageId) alt message already completed/failed/gone DO->>SQL: clearTurnParams(staleMessageId) else still pending — needs recovery DO->>DO: createMessage("assistant", new ID) DO->>SQL: saveTurnParams(newMessageId) DO->>SQL: insertEvent("message_failed", {staleMessageId, "interrupted"}) DO->>WS: broadcast(message_failed for stale message) DO->>SQL: insertEvent("thread_upserted", {headMessageId: newMessageId}) DO->>WS: broadcast(thread_upserted) DO->>SQL: insertEvent("message_upserted", {newMessage}) DO->>WS: broadcast(message_upserted for new message) DO->>AT: runAssistantTurn(original params + new message) AT-->>DO: turn completes DO->>SQL: clearTurnParams + deleteAlarm() end end end Note over WS: Client sees: old message → "interrupted"
new message appears → assistant starts responding

10. Optimistic Update Lifecycle

The lifecycle of an optimistic update: from dispatch through ack/reject/rollback.
stateDiagram-v2 [*] --> DISPATCHED: sendMessageAction() DISPATCHED --> OPTIMISTIC_APPLIED: applyLocalInsert/Update (collections) OPTIMISTIC_APPLIED --> AWAITING_ACK: dispatch via WebSocket AWAITING_ACK --> REJECTED: server sends "reject" AWAITING_ACK --> ACKNOWLEDGED: server sends "ack" ACKNOWLEDGED --> [*]: confirmOp() — clean up tracking REJECTED --> ROLLING_BACK: rollbackOp() ROLLING_BACK --> [*]: restore previous state state DISCONNECTED { [*] --> PENDING_LOCAL: op saved to localStorage PENDING_LOCAL --> REQUEUED: reconnect + flushAll() REQUEUED --> AWAITING_ACK } AWAITING_ACK --> DISCONNECTED: WebSocket closes DISCONNECTED --> AWAITING_ACK: reconnect + server dedup note right of AWAITING_ACK Server checks getCommandAck(opId) Already committed → re-ack only Not yet seen → process normally end note

The message types exchanged between client and server over the sync WebSocket.
