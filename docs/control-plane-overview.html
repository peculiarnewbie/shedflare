Proposed product direction

Shedflare becomes a personal software workshop.

People fork the source, choose the apps they want, deploy them to their own Cloudflare account, and then use coding agents to adapt the suite around their lives.

Shedflare is a forkable, agent-friendly personal software suite for Cloudflare.

The experience

From source code to a personal suite

The repository remains the product. The local Console becomes the clear path through setup and operations; agents enter after the user has a working base.

The Console

A control plane, not a god application

The Console gets much more responsibility—but only for operating the suite. Individual apps continue to own their behavior and data.

The Console should own

  • First-run setup and app selection
  • Credential guidance and secret rotation
  • Configuration, deployment, health, and drift
  • Backups, exports, and restore entry points
  • Agent customization handoff

The Console should not own

  • Money, Chat, Drive, or other app logic
  • App databases or duplicated Cloudflare state
  • A private configuration database
  • A deployment implementation separate from the CLI
  • Hidden, irreproducible mutations

The Console orchestrates Shedflare; it does not run Shedflare.

One engine, two interfaces

Console and CLI share headless operations

Console UI

The best human experience: guided, visual, progressive, and explanatory.

Shedflare core

Typed config, manifests, credentials, deployment, health, backups, and Git state.

CLI

The scriptable equivalent for CI, headless environments, power users, and agents.

Interactive actions always have a non-interactive equivalent.

State model

Keep three kinds of truth separate

Kind Examples Source of truth
Desired Domain, selected apps, non-secret preferences shedflare.config.jsonc
Secret API keys, OAuth secrets, signing keys Cloudflare secrets or gitignored local storage
Observed Workers, databases, deployed revision, health Cloudflare, Alchemy state, and Git

Config stays declarative, but hand-editing it stops being the onboarding experience.

Honest inventory

Apps can be unfinished without being confusing

Stable

Trusted with important data and backed by health, migration, and recovery practices.

Beta

Actively used but still changing or missing part of the operational contract.

Experimental

Exploratory, incomplete, and allowed to remain that way without blocking the suite.

Archived work remains available as source material but is not offered through normal setup. The Console and docs show these labels openly.

Delivery

Build it in safe vertical slices

  1. Contract and classification Agree on the product boundary and label every app honestly.
  2. Shared config and catalog core Make the Console and CLI read the same manifests and desired state.
  3. Setup wizard Select apps, configure defaults, preview the diff, and write valid config.
  4. Credentials Guide provider setup, validate access, and keep secret values out of config.
  5. Deployment and health Stream progress, attach Git revisions, and explain what is actually running.
  6. CI and operational safety Check the whole repo without fake app versions; standardize backup and restore.
  7. Agent handoff and consolidation Add focused recipes, prune misleading artifacts, and reduce speculative abstractions.

First practical milestone

Prove the boundary before touching secrets

Build now

  • Add lifecycle and setup metadata to manifests
  • Extract shared manifest/config operations
  • Add a /setup route
  • Select apps and preview config
  • Write only after confirmation and run validation

Deliberately defer

  • Cloudflare authentication
  • Secret mutation and OAuth setup
  • Deployment from the browser
  • Backups and restore
  • An embedded coding agent
